# 10. 구현 순서와 근무일별 통과 조건

## 1. 문서 목적

이 문서는 현재의 초기 골격에서 Stage 01 버티컬 슬라이스까지 어떤 순서로 구현할지 정의한다.

- `08_schedule.md`는 마일스톤 기간과 Go / No-Go 조건을 관리한다.
- 이 문서는 같은 기간 안의 코드 구현 순서, 선행 의존성, 일일 완료 조건을 관리한다.
- 범위와 기간이 충돌하면 `08_schedule.md`, 작업 선후관계가 충돌하면 이 문서를 우선한다.
- 모든 일정은 1인 개발, 하루 5~6시간, 주말 제외를 전제로 한 근무일 기준이다.

## 2. 현재 출발점

현재 저장소 상태는 다음과 같다.

- Godot 4.7 모바일 프로젝트 설정
- 실행용으로 등록된 부트스트랩 장면 `srcs/main.tscn`
- `state["screen"]`을 읽어 화면을 교체하는 `srcs/main.gd`
- 첫날 기본 상태와 로드 검증을 제공하는 `GameManager`
- `user://save.json` 입출력과 손상 파일 백업을 제공하는 `SaveManager`
- 인자 없는 `screen_change_requested`를 보내는 코드 기반 `LoadingScreen`
- 720 × 1280 회색 맵, 탭 목적지 이동, 충돌과 수동 카메라를 제공하는 코드 기반 `DayScreen`
- 우선순위와 거리로 접근 대상을 고르는 `DayInteractionController`
- 주문 수령, 고등어 상자, 밥통, 제작 게이지와 일시정지·재개를 연결한 코드 기반 고등어 제작 동선
- 손님의 착석·주문·서빙·식사·결제·퇴장과 최대 3명 FIFO 대기열
- 고등어 조리대 Lv.2와 좌석 2의 체류 결제, 즉시 수치·시설·배정 반영
- `tests/`를 자동 발견하는 GUT 설정과 기반 테스트
- 영업 종료·정산과 새벽 화면은 아직 없음

따라서 다음 구현 대상은 캐릭터나 최종 아트가 아니라 **영업 종료와 정산**이다.

## 3. 구현 우선순위

```text
실행 진입점·GameManager·테스트
→ 회색 맵·탭 이동·카메라
→ 접근 상호작용·고등어 제작
→ 손님 상태 흐름
→ 판매 전체 루프
→ 시설 성장
→ 점원 자동화
→ 영업 종료·정산
→ 시장·준비·Day 2
→ 통합·Android 빌드
```

다음 원칙을 모든 단계에 적용한다.

1. 선행 단계의 완료 조건이 실패하면 다음 기능을 시작하지 않는다.
2. P0에서는 최종 아트보다 플레이 가능한 데이터 흐름과 상태 복구를 우선한다.
3. 화면과 노드는 기존 부트스트랩 장면 아래에 GDScript로 구성한다.
4. 새 `.tscn`은 만들지 않는다. 필요하면 구현 전에 사용자 승인을 받는다.
5. Day, 단계, 시간, 통화, 재고, 해금과 진행도의 원본 상태는 `GameManager` 한 곳에 둔다.
6. P0에서는 임시 도형과 색상으로 상태를 구분하고 M3 전에는 최종 아트를 제작하지 않는다.

## 4. 입력과 카메라 계약

P0 입력은 다음 기준으로 구현한다.

- 고정 HUD 밖의 플레이 영역을 짧게 탭하면 해당 월드 위치로 이동한다.
- 시설이 가로막으면 40픽셀 A* 경로로 우회하고 통행 불가 위치는 가장 가까운 접근 가능 지점으로 보정한다.
- 캐릭터 애니메이션은 실제 이동 속도의 우세 축을 사용해 4방향으로 표시한다.
- 입력은 모바일 터치만 지원한다. PC 검증에서는 마우스 클릭으로 목적지를 지정하며 키보드 입력은 사용하지 않는다.
- 같은 플레이 영역을 8픽셀 이상 드래그하면 이동 명령 없이 카메라가 스테이지 경계 안에서 이동한다.
- PC 검증에서는 플레이 영역의 마우스 드래그가 카메라 터치를 대신한다.
- 카메라는 자동으로 플레이어를 따라가지 않으며 회전하거나 확대·축소하지 않는다.
- 이동 중 카메라를 드래그해도 기존 월드 목적지는 유지되고 새 탭은 이전 목적지를 교체한다.
- 단계가 바뀌면 카메라를 해당 단계의 기본 위치로 초기화한다.
- Day 1의 재료, 밥통, 고등어 조리대, 좌석 1, 입구는 초기 화면에 배치한다.

시설 뒤 목적지는 자동으로 우회하는 권장 기본값을 적용한다. 실제 기기 테스트에서 조작 피로가 확인되면 기능을 늘리기 전에 이동 속도, 경로 탐색 간격, 드래그 임계값과 맵 배치를 조정한다.

## 5. Milestone P0 — 10근무일

### Day 1 — 실행 기반과 상태 계약

**현재 상태: 구현 완료**

`GameManager.state` 기준으로 주문 수령부터 결제·퇴장까지 고등어 20접시를 연속 처리해 재료 0, 매출 120문, 빈 좌석·주문·결제 상태로 끝나는 회귀 테스트를 통과한다.

**구현**

- 기존 `srcs/main.tscn`을 실행용 메인 장면으로 등록한다.
- `Main`이 `GameManager.state["screen"]`을 읽어 코드 기반 화면을 교체하게 한다.
- 각 화면은 상태를 변경한 뒤 인자 없는 `screen_change_requested`를 발생시킨다.
- `LoadingScreen`이 로컬 JSON을 `GameManager.state`에 적용하거나 첫날 기본 상태를 생성하게 한다.
- `GameManager`에 Day, 하루 단계, 영업 시간, 통화, 재고, 해금, 강화와 누적 판매 초기 상태를 정의한다.
- `SaveManager`에 `user://save.json` 읽기·쓰기와 손상 파일 백업을 구현한다.
- GUT이 `tests/` 아래의 프로젝트 테스트를 발견하도록 구성한다.

**완료 조건**

- 프로젝트가 등록된 메인 장면으로 오류 없이 시작한다.
- 새 게임 초기값이 Day 1, 영업 단계, 0문, 밥 20, 고등어 20과 일치한다.
- 정상 JSON과 첫 실행 기본 상태가 `GameManager.state`에 깊은 복사된다.
- 손상 JSON은 자동으로 덮어쓰지 않고 Loading 화면에서 새 게임 선택을 기다린다.
- Main은 목적 화면이 미구현이면 Loading 화면을 유지한다.
- 프로젝트 테스트가 실제로 발견되고 Main·Loading·상태·저장 테스트가 통과한다.

### Day 2 — 회색 맵, 이동과 카메라

**현재 상태: 구현 완료**

**구현**

- Stage 01 회색 맵, 충돌 경계, 시작 시설 위치를 GDScript로 생성한다.
- 터치 탭과 PC 검증용 마우스 클릭을 월드 목적지 이동에 연결한다.
- 40픽셀 A* 경로 우회와 실제 속도 기반 4방향 표시를 구현한다.
- 플레이 영역 드래그, 카메라 경계, 단계별 기본 위치를 구현한다.
- 고정 HUD와 월드 좌표를 분리하고 탭·드래그를 구분한다.

**완료 조건**

- 짧은 탭이나 클릭으로 지정한 월드 목적지에 도착하면 멈춘다.
- 키보드 입력으로는 이동하지 않는다.
- 시설 뒤 목적지를 우회하고 시설 내부 탭은 가장 가까운 접근 위치에서 멈춘다.
- 카메라가 UI 드래그에 반응하지 않고 맵 경계를 벗어나지 않는다.
- 카메라 드래그는 이동 명령을 만들지 않고 진행 중인 이동을 취소하지 않는다.
- 캐릭터가 시설, 경계, 화면 밖에 영구적으로 끼지 않는다.

### Day 3 — 접근 상호작용과 고등어 제작

**현재 상태: 구현 완료**

**구현**

- 접근 가능한 대상의 탐색과 현재 대상 표시를 구현한다.
- 내려놓기, 주문 손님, 완성품, 재료, 엽전, 구매 패드 순으로 우선순위를 적용한다.
- 주문 수령, 고등어 상자, 밥통, 조리대 작업 게이지와 운반 상태를 연결한다.
- 밥과 고등어를 접시당 하나씩 소비한다.
- 고등어 주문 한 건마다 `주문 → 고등어 → 밥 → 조리대` 순서를 강제한다.
- 손님·엽전·구매 패드도 같은 우선순위 계약에 등록돼 있으며 새 접근 대상을 추가할 때 이 순서를 유지한다.

**완료 조건**

- 별도 제작 버튼 없이 접근만으로 고등어 접시를 만든다.
- 주문이나 재료 단계를 건너뛰고 조리대에 접근해도 제작되지 않는다.
- 재료가 부족하면 제작이 시작되지 않고 기존 상태가 보존된다.
- 겹친 대상에서도 정해진 우선순위가 항상 적용된다.
- 주문 수령부터 접시 완성까지 20회 반복해 중복 소비나 진행 정지가 없다.
- 제작 완료 시 해당 주문과 연결된 접시를 들며, 서빙 전에는 다음 주문을 받을 수 없다.

### Day 4 — 손님 상태 흐름

**현재 상태: 좌석 1의 생성·예약·착석·주문·식사·결제·퇴장, 3초 간격 최대 3명 FIFO 대기열과 빈 좌석 자동 승격까지 구현**

**구현**

- 입장, 대기, 착석, 주문, 식사, 결제 대기, 퇴장 상태를 명시적으로 구현한다.
- 좌석 예약과 반납, 최대 3명 대기열, 잠긴 메뉴 제외를 연결한다.
- P0 이동은 고정 접근 위치와 단순 경로를 사용하고 멈춤 감지를 둔다.

**완료 조건**

- 손님 10명이 연속으로 입장부터 퇴장까지 진행한다.
- 좌석과 대기열이 중복 배정되지 않는다.
- 퇴장하거나 복구된 손님이 주문과 좌석을 반드시 반납한다.
- 잠긴 계란 메뉴 주문이 생성되지 않는다.

### Day 5 — 판매 전체 루프

**현재 상태: 고등어 주문의 제작→서빙→식사→주문 생성 시점의 6문 또는 7문 결제→회수까지 구현, 실제 A* 이동 경로로 첫 판매 30초 게이트 통과**

**구현**

- 주문과 완성품을 일치시켜 서빙한다.
- 식사 후 판매가에 맞는 엽전을 생성하고 접근 시 회수한다.
- 재고, 현재 주문, 완성품, 보유금 HUD를 연결한다.
- 첫 판매까지 걸린 시간을 기록한다.

**완료 조건**

- 제작→서빙→식사→결제→회수가 끊기지 않는다.
- 주문과 다른 메뉴는 전달되지 않는다.
- 재료 차감, 판매가, 생성 엽전, 보유금이 일치한다.
- 새 게임 시작 후 첫 판매가 30초 안에 발생한다.

### Day 6 — 성장과 지출

**현재 상태: 고등어 조리대 Lv.2와 좌석 2의 구매 패드·결제·즉시 설치·수치 및 FIFO 배정 반영 완료**

**구현**

- 고등어 조리대 Lv.2와 좌석 2 구매 패드를 연결한다.
- 패드 체류 결제, 부족 금액 표시, 즉시 설치와 수치 갱신을 구현한다.
- 강화 수치는 한 GDScript 데이터 원본에서 읽는다.

**완료 조건**

- 첫 업그레이드가 60초 안에 가능하다.
- 보유금보다 비싼 구매는 실행되지 않는다.
- 같은 구매가 중복 결제되지 않는다.
- 좌석 2 해금 후 실제 동시 수요와 좌석 배정이 바뀐다.

### Day 7 — 점원 자동화

**현재 상태: 45문 체류 고용, 한 명 제한, 접시 예약→조리대 이동→수령→주문 확인→자동 서빙과 실패 복구 구현 완료, Day 8 영업 종료·정산이 다음 게이트**

**구현**

- 점원 고용 패드와 한 명 제한을 구현한다.
- 완성품 탐색, 주문 확인, 이동, 서빙의 명시적 상태 흐름을 만든다.
- 플레이어와 점원이 같은 접시를 예약하지 않게 한다.

**완료 조건**

- 점원 고용 후 10초 안에 자동 서빙을 시작한다.
- 주문과 일치하는 접시만 전달한다.
- 접시 예약과 손님 퇴장 중에도 중복 서빙이나 영구 정지가 없다.
- 플레이어는 제작과 엽전 회수를 계속 담당한다.

### Day 8 — 영업 종료와 정산

**구현**

- `GameManager` 영업 타이머, 마지막 주문, 조기 마감과 단계 전환을 연결한다.
- 판매량, 메뉴별 매출, 이탈, 남은 재료와 폐기량을 집계한다.
- 정산 UI를 GDScript로 생성한다.

**완료 조건**

- 타이머 종료 후 새 손님이 생성되지 않는다.
- 진행 중인 주문이 끝난 뒤 정산으로 이동한다.
- 판매량, 매출, 이탈, 폐기 수치가 실제 기록과 일치한다.
- 첫 정산이 게임 시작 후 약 6분에 발생한다.

### Day 9 — 시장, 배치 준비와 Day 2

**구현**

- 5인분 단위 쌀·고등어 구매와 구매 완료 전 전액 되돌리기를 구현한다.
- 운반→작업→보관의 배치 준비 흐름을 연결한다.
- 준비한 수량만 Day 2 판매 재고로 이전한다.
- 시장과 준비 단계의 기본 카메라 위치를 각각 지정한다.

**완료 조건**

- 구매 전액 되돌리기가 금액과 수량을 정확히 복원한다.
- 밥과 토핑을 최소 5인분 준비해야 다음 영업을 시작할 수 있다.
- 구매량, 준비량, Day 2 판매 가능량이 일치한다.
- 첫 정산 후 2분 안에 Day 2를 시작할 수 있다.

### Day 10 — 통합, 밸런스와 빌드

**구현**

- Day 1→정산→시장→준비→Day 2 전체 회귀 테스트를 추가한다.
- 첫 판매, 업그레이드, 점원, 정산, Day 2 시작 시간을 조정한다.
- Android 내보내기 프리셋을 구성하고 기준 기기용 테스트 빌드를 만든다.
- 알려진 버그와 P0 Go / No-Go 결과를 기록한다.

**완료 조건**

- Day 1→Day 2를 3회 연속 완주한다.
- 진행 불능과 크래시가 없다.
- 첫 판매 30초, 첫 업그레이드 60초, 첫 점원 5분, 첫 정산 6분, Day 2 시작 8분 목표를 충족한다.
- 최소 3명이 짧은 플레이테스트를 완료한다.
- Android 테스트 빌드가 기준 기기에서 실행된다.

### P0 실패 처리

P0 완료 조건 중 하나라도 실패하면 M1 또는 최종 아트로 넘어가지 않는다.

1. 실패한 지표와 재현 순서를 기록한다.
2. 2~3근무일 수정 스프린트를 삽입한다.
3. 이동 속도, 배치, 손님 간격, 비용 순으로 조정한다.
4. 같은 통합 테스트를 다시 3회 통과한 뒤 P0 승인 여부를 결정한다.

## 7. 일일 PM 운영

매 근무일 종료 시 아래 형식으로 기록한다.

```text
근무일:
상태: 시작 전 / 진행 중 / 통과 / 실패
오늘 완료한 사용자 가치:
자동 검증:
수동 검증:
새 위험:
막힌 항목:
다음 근무일 첫 작업:
범위 또는 일정 변경:
```

상태가 `실패`이면 다음 근무일 첫 작업은 실패 원인 수정이다. 완료 조건을 낮추거나 미완료 기능을 다음 마일스톤으로 넘기려면 PM이 범위와 일정을 함께 다시 승인한다.

## 8. 최종 구현 순서 수용 기준

- P0의 모든 기능이 정확히 하나의 근무일에 배정돼 있다.
- 각 근무일에 사용자에게 보이는 결과와 검증 가능한 완료 조건이 있다.
- `07_mvp_scope.md`의 포함 기능이 M4까지 모두 배정돼 있다.
- 제외 기능이 일정에 포함되지 않는다.
- 최종 아트는 P0 승인 이후에만 시작한다.
- 새 장면 파일 없이 기존 부트스트랩과 GDScript로 시작할 수 있다.
- 일정 지연 시 다음 기능을 병렬로 추가하지 않고 실패한 게이트부터 복구한다.
